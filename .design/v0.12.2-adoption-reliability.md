# Release: v0.12.2 adoption reliability

## Summary

`v0.12.2` closes three ordinary-use reliability gaps without making one agent
harness the owner of day's installation or verification model. Installation
guidance becomes a portable skill and document contract, the behaviour-diff
harness leaves the default Cargo suite for a dedicated serialized CI gate, and
kan trust narrowing uses the per-subject evidence already present in
`status --json`. The changes land as independently reviewable pull requests;
the release cut is the boundary that requires all three to be merged and green.

This work serves `telos/v1.0` by making first use less dependent on the author,
`telos/affordance-not-enforcement` by keeping missing prerequisites advisory,
and `telos/honest-reads` by refusing only where kan's evidence warrants it.

## Requirements

- REQ-1: The portable plugin surface treats `day` and `kan` as externally
  installed prerequisites, matching the bare `day` command in `mcp.json`.
  Neither `plugin.json` nor a harness adapter claims to bundle or install the
  binaries.

- REQ-2: Installation and missing-command recovery are available without
  executing Node, Bash, PowerShell, Python, or day itself. A shipped Agent Skill
  and `docs/GETTING_STARTED.md` provide platform-specific routes to install the
  pinned day/kan pair, distinguish Cargo-present from Cargo-absent systems, and
  end with the same verification commands.

- REQ-3: Claude Code's `hooks/hooks.json` contains no bootstrap program whose
  only purpose is detecting that `day` or `kan` is absent. Claude-specific
  hooks may invoke day after installation, but installation ownership remains
  in the harness-neutral plugin surface. A missing binary is never converted
  into a blocking hook decision.

- REQ-4: The installation version pair has one derived source of truth. Tests
  fail if the skill, README, `docs/GETTING_STARTED.md`, plugin metadata, or
  release metadata names a stale day or kan version.

- REQ-5: `tests/behaviour_diff.rs` remains locally runnable but does not execute
  nested Cargo builds during the default `cargo test --workspace` suite. Its
  four harness-integrity checks run through one documented dedicated command.

- REQ-6: CI runs the dedicated behaviour-diff command as a required, visibly
  named gate with one test thread and no concurrent Cargo-producing step in
  that job. A skipped or absent behaviour-diff execution cannot be reported as
  a successful verification.

- REQ-7: The behaviour-diff harness preserves its fail-safe semantics:
  HEAD-DID-NOT-BUILD and BASE-DID-NOT-BUILD remain could-not-check outcomes,
  never IDENTICAL, and moving the tests does not weaken their assertions or
  hide a real build failure.

- REQ-8: `src/kan_client.rs` parses both the log-wide and per-subject
  `excluded_by_trust` fields from the real `kan status --json` envelope. A
  subject with an attributed withheld count is refused using subject-specific
  evidence; an unrelated withheld claim elsewhere in the log does not make a
  genuinely absent subject unreadable.

- REQ-9: Every writer of the log-wide withheld count uses one explicit,
  order-independent reconciliation rule. Reading `status --json` before or
  after `show --all --json`, including when either envelope omits or reports a
  lower count, yields the same conservative total.

- REQ-10: `tests/kan_conformance.rs` pins the real `status --json` top-level and
  per-subject trust fields across every kan version in the compatibility
  matrix. Stub tests separately cover disagreement between envelopes and do
  not substitute for the real-binary check.

- REQ-11: The #177, #167, and #162 changes are independently reviewable and may
  land in separate pull requests. The `v0.12.2` release is not cut until all
  three dispositions are merged, their required CI gates pass, version-bearing
  files move coherently, and the published artifact is verified.

## Architecture

### Portable installation surface (#177)

The plugin remains an adapter to installed binaries. `mcp.json` is the
harness-neutral executable contract and continues to resolve `day` through the
platform's PATH. A new installation skill under `skills/` carries instructions
rather than executable bootstrap logic, so any Agent Skills consumer can render
or act on them without a language runtime chosen by day. `README.md` and
`docs/GETTING_STARTED.md` remain the human-readable entry points.

The skill branches in prose on observable capabilities: when Cargo exists, the
same pinned `cargo install` pair works on supported platforms; when it does not,
the skill gives platform-specific Rust/toolchain or release-artifact routes and
asks the user before installation. It does not silently download software.
`hooks/bootstrap-check.js` and the older shell implementation are removed from
the Claude adapter, and `hooks/hooks.json` retains only post-install day hooks.
`tests/agent_plugins.rs`, `tests/plugin.rs`, and `tests/install_docs.rs` pin the
boundary and derive the version pair.

This deliberately gives up automatic SessionStart detection. Agent Plugins has
no portable dependency-installer runtime or platform-conditional component,
and Claude Code's native installation no longer guarantees Node. A harness may
surface its own missing-command diagnostic; day provides the recovery path as
portable content rather than pretending one harness's runtime is universal.

### Dedicated behaviour-diff gate (#167)

`tests/behaviour_diff.rs` is a verifier of `scripts/behaviour-diff.py`, and the
script itself invokes Cargo for HEAD and worktree builds. Those recursive builds
do not belong inside the default Cargo test scheduler. The tests become an
explicitly selected target or ignored group invoked by one repository script or
Cargo command with `--test-threads=1`. `.github/workflows/ci.yml` runs it in a
dedicated job whose steps are sequential and whose result is independently
visible.

Contention detection is rejected: Cargo's lock message is not a stable API, is
observed only after work may already have blocked, and skipping would turn a
verification absence into green. An internal file lock is also rejected because
it cannot coordinate with unrelated Cargo processes. The dedicated job controls
the concurrency it owns; local callers opt into an expensive verifier and see
its could-not-check result if their wider machine is contended.

### Per-subject withheld evidence (#162)

`SubjectsEnvelope` and its subject entry in `src/kan_client.rs` retain
`excluded_by_trust` from `kan status --json`. `KanClient::subject_names` stores
that attribution beside the existing bulk-read attribution, merging by subject
with a conservative maximum. Both envelope readers update
`trust_withheld_total` through one helper using the maximum, so neither call
order nor a missing/lower field can erase evidence already observed.

`KanClient::show` uses per-subject attribution before falling back to the
existing unaccounted and log-wide uncertainty rules. Enumerating readers retain
the log-wide warning, but a targeted lookup is no longer over-refused merely
because another subject was withheld. `tests/kan_conformance.rs` measures the
real status envelope, while hermetic fixtures in `tests/fallbacks.rs` and
`tests/cli.rs` cover disagreement and rendering.

### Release coordination

The three mechanisms do not share a code path and therefore do not share an
implementation branch. Their shared invariant is adoption reliability, and the
release gate—not a combined diff—is where they compose. `CHANGELOG.md`, version
manifests, install pins, compatibility fixtures, and release claims move only
after the independently reviewed changes are on main.

## Resolved Questions

- RQ-1: Installation guidance is harness-neutral content, not a Node bootstrap
  hook. Platform-specific instructions ship together in a portable skill and
  documentation.
- RQ-2: Behaviour-diff moves out of the default suite into a dedicated,
  serialized, required CI gate; it is not skipped by parsing Cargo lock text.
- RQ-3: Per-subject `excluded_by_trust` is consumed in v0.12.2 rather than
  deferring to log-wide accounting only.
- RQ-4: The mechanisms land as separate pull requests and the release cut waits
  for all of them.

## Open Questions

None.

## Out of Scope

- Adding dependency installation semantics to the Agent Plugins specification.
- Bundling day or kan binaries inside a plugin or creating a second binary
  release channel.
- Automatically downloading or executing installers without user approval.
- Making all Unix-only integration tests compile on Windows.
- Eliminating contention from arbitrary Cargo processes outside the dedicated
  CI job.
- Changing kan's trust model or recovering the names of subjects kan omits from
  both JSON envelopes.
- Starting v0.13 workflow ergonomics or v0.14 vocabulary-pack work.
