# v0.12.2 adoption reliability trial — protocol v1

This protocol is fixed before implementation is accepted. A run may append raw
evidence and a verdict; it may not weaken or omit a row after seeing its result.

The reproducible runner is
`.github/workflows/adoption-reliability-trial.yml`. Dispatch it with the exact
RC commit SHA. Each row uploads its raw evidence even on failure; the final job
refuses unless every required row completed successfully. A green workflow is
an evidence bundle, not the attestation—the operator reviews the artifacts
before recording the Result below.

## Release candidate

Run against installed artifacts built from the exact v0.12.2 release-candidate
commit. Source-tree binaries, pre-existing Cargo installs, repository-local
PATH entries, and author configuration invalidate the run.

## Required matrix

1. Agent Skills consumer on macOS or Linux, starting without day and kan.
2. Agent Skills consumer on native Windows, starting without day and kan.
3. Claude Code adapter on either platform, with Node absent from PATH, proving
   the adapter has no bootstrap-runtime dependency and that the portable
   installation skill remains discoverable.

Each environment must be newly provisioned or accompanied by a before-snapshot
that proves the same clean state. The operator follows only the shipped plugin,
README, and getting-started guidance. Any undocumented intervention fails the
row.

## Installation checks

For every row, preserve the commands, stdout, stderr, exit status, OS, harness
version, plugin commit, and installed binary versions. The platform-appropriate
guidance must lead, with explicit approval for installation, to successful:

```text
kan --version
day --version
day doctor
```

## Behaviour-diff controls

With an unrelated Cargo build active on the machine:

1. Run the ordinary workspace suite and prove from a positive invocation
   counter that `scripts/behaviour-diff.py` ran zero times.
2. Stop or isolate the unrelated build, then run the documented dedicated
   behaviour-diff command. Every ignored test must run exactly once with one
   test thread and produce a real pass/fail verdict.
3. Inject the preregistered HEAD-build and base-build failures. Each must remain
   a distinct non-zero could-not-check result, never IDENTICAL or skipped.

## Trust controls

Use a scratch kan repository with two admitted identities and controlled
`excluded_by_trust` counts. Preserve both `status --json` and
`show --all --json` envelopes. Verify:

1. a subject with a withheld newest claim is refused as partial;
2. a genuinely absent subject remains absent when every withheld claim is
   attributed to another subject;
3. an absence remains indeterminate when the envelope total exceeds the sum of
   attributed subject counts; and
4. a subject returned by status but omitted unexpectedly by the bulk read is
   reported unaccounted.

Run the status-first and bulk-first orders; answers and conservative totals
must agree.

## Verdict

The trial passes only when every matrix row and every positive and negative
control passes, all raw evidence is retained, and no undocumented intervention
occurred. A skipped row, source-tree substitution, missing output, ambiguous
result, or could-not-check outside the two deliberately injected build failures
is a failed trial.

Record a passing attestation as a Result on
`trial/v0.12.2-adoption-reliability` whose text starts exactly with:

```text
adoption reliability trial PASSED (protocol v1, rc v0.12.2)
```

A failure may be recorded, but it must not use that prefix.
